# Отчет: задачи, отложенные задачи, публикации и отложенные публикации

> Документ создан после анализа новых файлов в папке `important files` и рефакторинга UI.
> Здесь простыми словами описано, что теперь происходит на бэкенде на каждом шаге, какие сценарии поддерживаются, что изменено во фронтенде, и дана оценка архитектуры.

---

## 1. Что изменилось в логике (кратко)

Раньше, судя по текущему UI, было два почти независимых пути:

1. **Мгновенное изменение цен** — пользователь нажимает «Применить», бэкенд сразу меняет цены.
2. **Публикация события** — после изменения цен фронт отдельно просил создать публикацию через `/api/publisher`.

Теперь на бэкенде появился единый механизм **отложенных задач**:

- Задача (task) — это запись «сделать действие в будущем».
- Публикация (published event) — это запись «показать событие на главной странице».
- Задача может быть связана с публикацией через поле `taskId`.
- Когда задача выполняется, обработчик (handler) делает полезное действие (например, меняет цены), а затем, если нужно, «активирует» связанную публикацию.

Появились новые строительные блоки:

- `TaskStatus` — статус задачи: `PLANNED`, `COMPLETED`, `CANCELED`, `ERROR`.
- `TaskType` — тип задачи/публикации: `CHANGE_PRICE`, `NEWS`, `START_OF_SALES`.
- `EventStatus` — статус публикации: `SCHEDULED`, `PUBLISHED`, `ARCHIVED`.
- `ScheduledTaskProcessor` — фоновый компонент, который каждую минуту ищет задачи, у которых наступил срок выполнения.
- `ScheduledTaskExecutionService` — выполняет задачу в транзакции (транзакция — это «всё или ничего»: либо все изменения сохраняются, либо не сохраняется ничего).
- `TaskHandler` / `TaskHandlerRegistry` — паттерн «обработчик + реестр», чтобы легко добавлять новые типы задач.

---

## 2. Основные понятия (словарь)

| Термин | Простое объяснение |
|---|---|
| **Задача (ScheduledTask)** | План на будущее: «в такое-то время сделай такое-то действие». |
| **Payload** | JSON-строка с параметрами задачи. Например, для изменения цены там лежит фильтр, тип изменения, значение и направление (плюс/минус). |
| **Deadline / deadLine** | Момент времени, когда задачу нужно выполнить. |
| **Обработчик (TaskHandler)** | Класс, который умеет выполнять конкретный тип задачи. |
| **Реестр обработчиков (TaskHandlerRegistry)** | Список всех обработчиков, по которому система находит нужный по типу задачи. |
| **Публикация (PublishedEvent)** | Запись о событии, которое показывается на главной странице. |
| **Транзакция (transaction)** | Группа операций, которые выполняются атомарно: если хоть одна упала, откатываются все предыдущие. |
| **Пессимистичная блокировка (pessimistic lock)** | Способ запретить другим потокам/серверам одновременно менять одну и ту же задачу. |
| **Идемпотентность (idempotency)** | Свойство операции: сколько раз её ни повторяй, результат не меняется (или повторное выполнение безопасно). |

## 3. Как устроен процесс выполнения отложенных задач

Часть `ScheduledTaskProcessor` работает в фоне примерно так:

1. Каждые 60 секунд (после завершения предыдущего прохода) вызывается `processDueTasks()`.
2. Делается запрос в базу: «найди id задач, у которых статус `PLANNED` и `deadLine <= сейчас`».
3. Для каждого id вызывается `executionService.execute(id)`.
4. `execute` берёт задачу из базы **с пессимистичной блокировкой** и только если она всё ещё `PLANNED`. Если другой сервер уже взял эту задачу — второй сервер просто ничего не делает.
5. Выполняется нужный обработчик.
6. Если успех — статус задачи становится `COMPLETED`.
7. Если нужно — активируется связанная публикация.
8. Если при выполнении обработчика упала ошибка — процессор ловит исключение и переводит задачу в `ERROR` (отдельной транзакцией, чтобы ошибка сохранилась даже при откате основной).

Это даёт защиту от **двойного выполнения** в многопоточной/многосерверной среде: блокировка + условие `status = PLANNED` не дают выполнить задачу дважды.

## 4. Подробные сценарии

Ниже разобраны все основные сценарии, которые есть в UI.

---

### Сценарий 1. Отложенное изменение цен **без** публикации

**Что делает пользователь в UI:**
Открывает «Матрицу цен», настраивает область/типы/расчёт, нажимает «Запланировать задачу», выбирает дату и время, на вопрос «Опубликовать событие?» отвечает **«Нет»**.

**Что происходит на бэкенде по шагам:**

1. Фронт отправляет `POST /api/scheduled-tasks/price-change` с телом:
   ```json
   {
     "deadLine": "2025-12-01T10:00:00",
     "publishNews": false,
     "publishStartDate": "2025-12-01",
     "filter": { ... },
     "typeChange": "PERCENT",
     "value": 5,
     "arithmeticalOperation": true
   }
   ```
2. `ScheduledService.schedulePriceChange(...)` собирает `PayloadChangePriceTask` — это просто набор параметров задачи.
3. Параметры превращаются в JSON (`payload`) и сохраняется новая запись `ScheduledTask`:
   - тип `CHANGE_PRICE`
   - статус `PLANNED`
   - `deadLine` — выбранное пользователем время
   - `publishNews = false`
   - `userId = 0` (сейчас система не различает пользователей)
   - `created = сейчас`
4. Так как `publishNews = false`, публикация **не создаётся**.
5. Пользователю возвращается `ScheduledTaskOutDto` (id, дата, тип, статус и т.д.).
6. Каждую минуту `ScheduledTaskProcessor` находит эту задачу, как только `deadLine` станет меньше или равен текущему времени.
7. `ScheduledTaskExecutionService.execute(...)`:
   - находит задачу с блокировкой и статусом `PLANNED`;
   - находит обработчик по типу `CHANGE_PRICE` через `TaskHandlerRegistry`;
   - обработчик `ChangePriceTaskHandler` читает `payload`, превращает JSON обратно в объект и вызывает `apartmentService.priceMatrix(...)`.
8. `priceMatrix(...)` меняет цены у подходящих квартир (статус «Свободна» и подходящий фильтр).
9. Если всё хорошо, задача переводится в `COMPLETED`. Транзакция фиксируется: и изменение цен, и статус задачи сохраняются вместе.

**Итог:** цены изменятся автоматически в выбранное время. Публикации на сайте не будет.

---

### Сценарий 2. Отложенное изменение цен **с немедленной публикацией-анонсом**

**Что делает пользователь:**
Настраивает матрицу цен, жмёт «Запланировать задачу», на вопрос о публикации выбирает **«Да, опубликовать»** и режим **«Сразу (с сегодняшнего дня)»**.

**Что происходит на бэкенде по шагам:**

1. Фронт отправляет такой же `POST /api/scheduled-tasks/price-change`, но:
   - `publishNews = true`
   - `publishStartDate = сегодня` (текущая дата) — публикация-анонс начинается сразу; окончание публикации = дата `deadLine`
2. `ScheduledService` сохраняет задачу точно так же, как в сценарии 1.
3. Так как `publishNews = true`, вызывается `createPublishEvent(...)`:
   - берётся название ЖК и ключ картинки-рендера;
   - создаётся `PublishedEventDTO` с типом `CHANGE_PRICE`, полями дат, названием ЖК, картинкой;
   - этому DTO проставляется `taskId` — id только что сохранённой задачи.
4. `PublishedEventsService.createEvent(...)` сохраняет публикацию:
   - `eventContent` формируется по шаблону **«будет»**: например, `"01.12.2025 будет изменение цены в ЖК Пример"`;
   - статус `PUBLISHED`, так как дата начала = сегодня (если бы дата была в будущем — был бы `SCHEDULED`);
   - даты: начало — `publishStartDate`, конец — дата `deadLine`.
   Это по сути «черновик»/анонс, привязанный к задаче.
5. Когда наступает `deadLine`, фоновый процессор выполняет задачу:
   - обработчик меняет цены;
   - статус задачи становится `COMPLETED`;
   - вызывается `publishedEventsService.activateScheduledEvent(taskId, сегодня)`.
6. `activateScheduledEvent` находит публикацию по `taskId` и «активирует» её:
   - контент меняется на шаблон **«произошло»**: например, `"01.12.2025 произошло изменение цены в ЖК Пример"`;
   - тип меняется на `NEWS` (теперь это обычная новость);
   - дата окончания становится `сегодня + 3 дня`;
   - статус становится `PUBLISHED`.
7. До выполнения задачи публикация имеет старт = сегодня и конец = `deadLine`, поэтому она видна на сайте как анонс `CHANGE_PRICE`. После выполнения она становится `NEWS` с концом = сегодня + 3 дня.

**Итог:** публикация-анонс появляется сразу с текущей даты и живёт до `deadLine`; в момент выполнения цены меняются, и та же публикация превращается в `NEWS` ещё на 3 дня.

### Сценарий 3. Отложенное изменение цен **с отложенной публикацией** (старт публикации задаёт пользователь)

**Что делает пользователь:**
То же самое, что в сценарии 2, но при вопросе «Когда опубликовать?» выбирает **«Отложить»** и указывает свою дату начала публикации. На фронте эта дата не может быть раньше сегодня и не может быть позже даты выполнения задачи.

**Что должно происходить на бэкенде:**

1. Задача сохраняется как обычно.
2. Публикация создаётся с `startEventDate` = выбранная пользователем будущая дата.
3. В день выполнения меняются цены.
4. Публикация должна «дождаться» своей даты начала и потом показываться на сайте.

**Что сейчас реально делает код из `important files`:**

1. `ScheduledService.createPublishEvent` создаёт публикацию с `endEventDate = LocalDate.from(deadLine)`.
2. Если пользователь выбрал `startEventDate` позже даты `deadLine`, то изначально получается диапазон, где **конец раньше начала** (`start > end`). Такая публикация не может быть активной по запросу `findActiveEvents`.
3. При активации `activateScheduledEvent` код меняет `endEventDate` на `сегодня + 3 дня`, но **не меняет `startEventDate`**.
4. Если `startEventDate` всё ещё позже, чем `сегодня + 3 дня`, диапазон снова получается «перевёрнутым» (`start > end`) и событие не появится.

**Вывод:** на фронте теперь стоит защита `start <= deadline`, поэтому из UI некорректный диапазон уйти не может. На бэкенде всё равно стоит добавить аналогичную валидацию, чтобы защититься от прямых запросов к API с `start > deadline`.

### Сценарий 4. Мгновенное изменение цен **без** публикации

**Что делает пользователь:**
В «Матрице цен» жмёт «Применить» и подтверждает.

**Что происходит:**
- Фронт вызывает старый/текущий endpoint `PUT /api/apartments/price-matrix`.
- Бэкенд сразу меняет цены.
- Никакой задачи и публикации не создаётся.
- В UI показывается результат: сколько квартир изменено.

Этот сценарий **не использует** новые `ScheduledTask` / `ScheduledTaskProcessor`.

### Сценарий 5. Мгновенное изменение цен **с публикацией**

**Что делает пользователь:**
Жмёт «Применить», после успешного изменения цен модалка спрашивает «Опубликовать событие?», пользователь выбирает «Да».

**Что происходит:**
1. Фронт вызывает `PUT /api/apartments/price-matrix` — цены меняются сразу.
2. Затем фронт вызывает `POST /api/publisher` с телом:
   ```json
   {
     "type": "NEWS",
     "content": "В ЖК «Пример» произошло изменение цен: ...",
     "startEventDate": "сегодня",
     "endEventDate": "сегодня + 3 дня",
     "eventPictureKey": "ключ картинки"
   }
   ```
3. Бэкенд сохраняет `PublishedEvent` через `PublishedEventsService.createEvent`.
4. Публикация сразу активна (даты подходят), поэтому появляется на главной.

Здесь нет задачи и нет `taskId`. Это отдельный упрощённый сценарий для «сделали сейчас и хотим показать новость».

### Сценарий 6. Прямое создание публикации через API

`POST /api/publisher` умеет принимать `PublishedEventDTO`:

- `type` — тип события;
- `targetName` — название объекта;
- `content` — текст новости;
- `startEventDate` — дата начала показа;
- `endEventDate` — дата окончания;
- `eventDate` — опциональная дата события;
- `taskId` — связь с задачей (если есть);
- `eventPictureKey` — ключ картинки.

`GET /api/publisher` возвращает события, у которых:
- `startEventDate <= сегодня`
- `endEventDate >= сегодня`

То есть именно те события, которые сейчас нужно показывать на главной.

## 5. Взаимосвязь задач и публикаций

Связь идёт через поле `taskId` в таблице `published_event`:

```
ScheduledTask (id=10, type=CHANGE_PRICE, publishNews=true)
    ↓
PublishedEvent (taskId=10, type=CHANGE_PRICE, status=SCHEDULED)
    ↓ (при выполнении задачи)
PublishedEvent (taskId=10, type=NEWS, status=PUBLISHED, end=today+3)
```

Зачем это нужно:
- Пока задача не выполнена, публикация знает, к какой задаче относится.
- При выполнении задачи система находит публикацию по `taskId` и обновляет её: текст, тип, даты, статус.
- Это позволяет не плодить дубликаты: у задачи может быть ровно одна связанная публикация (по задумке).

## 6. Что изменено в UI

Я проанализировал текущий фронтенд (`PriceMatrixModal.vue`, `HomeEventsSlider.vue`, `src/api/index.js`). Основной сценарий уже был реализован: модалка «Матрица цен» умеет и мгновенное применение, и планирование задачи, и вопрос про публикацию.

Найденные проблемы в UI и их исправления:

### 1. `publishStartDate` уходил `null`

- DTO бэкенда `SchedulePriceChangeRequestDTO` помечает `publishStartDate` как `@NotNull`.
- Раньше при `publishNews = false` фронт отправлял `publishStartDate: null`.
- Теперь фронт всегда передаёт валидную дату: при публикации — нужную пользователю, без публикации — дату `deadLine`.

### 2. Мгновенная публикация после мгновенного изменения цен была слишком длинной

- Раньше фронт отправлял `endEventDate = сегодня + 30 дней`.
- По новой логике нужно `endEventDate = сегодня + 3 дня`.
- Исправлено в `sendImmediatePublish`.

### 3. Отложенная задача + «немедленная публикация» отправляла неправильный старт

- Раньше фронт отправлял `publishStartDate = дата deadLine`.
- По новой логике для немедленной публикации `publishStartDate = сегодня`, а окончание публикации = `deadLine`.
- Исправлено в `sendScheduledTask`: при режиме "Сразу (с сегодняшнего дня)" старт публикации становится `todayIso`.

### 4. Отложенная публикация не давала выбрать дату раньше deadLine

- Раньше поле выбора даты имело `min = deadLine`.
- Теперь `min = сегодня`, `max = deadLine`.
- Пользователь может выбрать любую дату от сегодня до даты выполнения задачи.
- Добавлена проверка: `startDate > deadlineDate` → ошибка.

## 7. Анализ архитектуры бэкенда

### 7.1 Расширяемость (extensibility)

**Что хорошо:**
- Паттерн `TaskHandler` + `TaskHandlerRegistry` позволяет добавлять новый тип задачи без изменения процессора. Достаточно:
  1. добавить значение в `TaskType`;
  2. написать класс с интерфейсом `TaskHandler`;
  3. пометить его `@Component`;
  Реестр сам подхватит его через список всех обработчиков.
- `Payload` хранится как JSON, поэтому параметры каждой задачи могут быть разными.
- `PublishedEvent` имеет `TaskType` и общие поля (`targetName`, картинка, даты), что удобно для разных типов публикаций.

**Что можно улучшить:**
- Сейчас есть только `POST /api/scheduled-tasks/price-change`. Нет универсального endpoint'а «создать задачу любого типа». Это ограничивает расширяемость: для нового типа задачи придётся добавлять отдельный метод/контроллер.
- Нет CRUD для задач: нельзя посмотреть список запланированных задач, отменить или удалить. Статус `CANCELED` есть, но в UI/API не используется.

### 7.2 Оптимизация (optimization)

**Что хорошо:**
- `ScheduledTaskRepo.findDueTaskIds` выбирает только id просроченных задач, а не все строки таблицы.
- Пессимистичная блокировка `PESSIMISTIC_WRITE` защищает от двойного выполнения в мультисерверной среде.
- `findPlannedTaskByIdForUpdate` дополнительно фильтрует по статусу `PLANNED`, поэтому уже выполненная или ошибочная задача не будет взята снова.

**Что стоит проверить/улучшить:**
- Если задач станет очень много, опрос «каждую минуту все просроченные id» может стать узким местом. Стоит повесить индекс на `(status, deadLine)`.
- Запрос `findActiveEvents` не фильтрует по `status`. Если появятся `ARCHIVED`-события или `SCHEDULED`, попавшие в даты, они могут случайно показываться на сайте. Лучше добавить условие `status = 'PUBLISHED'` или отдельную логику перехода из `SCHEDULED` в `PUBLISHED`.
- `findByTaskId` в `PublishedEventsRepo` предполагает, что `taskId` уникален. Если уникальности нет, метод вернёт исключение при дублях. Рекомендуется поставить unique-индекс/колонку.

### 7.3 Идемпотентность (idempotency)

**Что хорошо:**
- Повторный запуск одной и той же задачи невозможен: блокировка и статус `PLANNED` не дают выполнить `COMPLETED`-задачу повторно.
- `markErrorIfPlanned` меняет статус только у `PLANNED`, поэтому не затрёт `COMPLETED`.
- `activateScheduledEvent` содержит защиту:
  ```java
  if (event.getStatus() == EventStatus.PUBLISHED && event.getType() == TaskType.NEWS) return false;
  ```
  Это предотвращает повторную «активацию» уже активированной публикации.
- Мгновенное изменение цен и статус задачи находятся в одной транзакции: если одно упало, откатится и второе.

**Что можно улучшить:**
- Сам обработчик изменения цен не является идемпотентным в строгом смысле. Если когда-нибудь выполнение задачи повторится из-за внешних причин (например, после долгого зависания и ручного перезапуска), цены могут быть изменены повторно. Сейчас транзакция это почти исключает, но для полной надёжности можно добавить `idempotency key` или версию задачи.
- Создание задач и публикаций через API не защищено от дубликатов: если фронт дважды отправит `POST`, создадутся две задачи/публикации. Можно добавить уникальный ключ клиента (`requestId`).

### 7.4 Общая архитектура

**Сильные стороны:**
- Чёткое разделение: контроллеры → сервисы → репозитории.
- Отдельный слой обработчиков задач.
- Фоновая обработка вынесена в отдельный компонент.
- Транзакционные границы выставлены разумно.
- Понятные enum'ы и привязка публикации к задаче.

**Слабые стороны / риски:**

1. **Контроллер публикаций возвращает сущность напрямую**
   `PublisherEventsController.getEvents()` возвращает `List<PublishedEvent>`, а не DTO. Это связывает API с таблицей БД: изменение сущности может сломать клиентов. Лучше отдавать отдельный out-DTO.

2. **Статус `EventStatus` используется не полностью**
   В `findActiveEvents` нет фильтра по статусу. Если событие должно быть скрыто (например, `ARCHIVED`), одного «не совпали даты» недостаточно.

3. **Логика отложенной публикации после отложенной задачи не работает**
   Как описано в сценарии 3, `startEventDate` и `endEventDate` могут «перевернуться». Нужно пересматривать и начало, и конец при активации.

4. **DTO требует `publishStartDate` всегда**
   Это неудобно: поле не нужно, когда `publishNews = false`. Лучше сделать валидацию группы: `@NotNull` только когда `publishNews = true`, либо разрешить `null`.

5. **Нет user story для отмены задач**
   `TaskStatus.CANCELED` заявлен, но нет ни endpoint'а, ни UI. Если функциональность не нужна — лучше убрать, если нужна — добавить API.

6. **Нет общего endpoint'а для списка задач**
   Администратор не видит, какие задачи запланированы, какие завершились, какие упали. Для наблюдаемости полезно добавить `GET /api/scheduled-tasks`.

## 8. Рекомендации по доработке

1. **Исправить активацию отложенной публикации**
   При `activateScheduledEvent` нужно гарантировать `startEventDate <= endEventDate`. Например:
   - если `startEventDate` в будущем, то `endEventDate = startEventDate.plusDays(3)`;
   - если `startEventDate` уже прошло/сегодня, то `startEventDate = activationDate`, `endEventDate = activationDate.plusDays(3)`.

2. **Добавить уникальный индекс на `PublishedEvent.taskId`**
   Это защитит от дублей и сделает `findByTaskId` безопасным.

3. **Фильтровать события по статусу в `findActiveEvents`**
   Например, `WHERE e.status = com.search_service.entity.EventStatus.PUBLISHED AND ...`.

4. **Добавить API для управления задачами**
   `GET /api/scheduled-tasks` (список), `DELETE /api/scheduled-tasks/{id}` (отмена) или `POST /api/scheduled-tasks/{id}/cancel`.

5. **Добавить idempotency key**
   Клиент может слать `requestId`, а сервер — отклонять повторные запросы с тем же `requestId`.

6. **Выводить сущности через DTO**
   Не возвращать `PublishedEvent` напрямую из контроллера.

7. **Условная валидация `publishStartDate`**
   Перестать требовать дату начала публикации, когда `publishNews = false`.

## 9. Найденная ошибка: `task_id NOT NULL`

При мгновенном изменении цен с публикацией фронт создаёт событие напрямую через `POST /api/publisher`. В этом сценарии задачи нет, поэтому `taskId` не передаётся — это правильно по логике.

Но в базе данных колонка `published_event.task_id`, судя по ошибке, имеет `NOT NULL`. Из-за этого вставка падает:

```
null value in column "task_id" of relation "published_event"
violates not-null constraint
```

**Причина:** рассинхрон между схемой БД и Java-моделью. В `PublishedEvent.java` поле `taskId` объявлено как обычное `@Column(name = "task_id")`, без `nullable = false`, то есть JPA считает его необязательным. Но реальная колонка в БД создана как `NOT NULL`.

**Как исправить на бэкенде:**
1. Выполнить миграцию БД:
   ```sql
   ALTER TABLE published_event ALTER COLUMN task_id DROP NOT NULL;
   ```
2. В сущности `PublishedEvent` оставить поле nullable (либо явно написать `nullable = true`).
3. Проверить, что прямой `POST /api/publisher` с любым типом (`NEWS`, `CHANGE_PRICE`, `START_OF_SALES`) работает без `taskId`.

**Аналогичная проблема:** любой прямой вызов `/api/publisher` без `taskId` будет падать одинаково, пока колонка `task_id` NOT NULL. Это касается не только мгновенной публикации после изменения цен, но и всех ручных публикаций.

## 10. Итог

Новая архитектура в целом правильная и гибкая:

- есть отложенные задачи,
- есть обработчики,
- есть связь задачи с публикацией,
- есть защита от повторного выполнения через блокировки.

В UI дополнительно исправлено:
- мгновенная публикация после изменения цен теперь всегда `start = сегодня`, `end = сегодня + 3 дня`;
- из мгновенной публикации убрана логика отложенной публикации;
- отложенная задача с немедленной публикацией шлёт `publishStartDate = today`;
- отложенная публикация ограничена диапазоном `today..deadline`;
- уведомления о задаче теперь показывают дату исполнения и дату начала публикации;
- после успешного применения/планирования модалка «Матрица цен» автоматически закрывается.

Осталось главное на бэкенде:
- сделать `published_event.task_id` nullable;
- добавить защиту `publishStartDate <= deadline` на уровне API.
